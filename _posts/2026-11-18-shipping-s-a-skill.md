# Shipping Is a Skill

## (And Most Indie Developers Don't Practice It Enough)

There is a version of game development that never ends. The scope expands a little each week. Features get added because they'd be cool to have. Systems get refactored because they could be cleaner. Levels get polished because they aren't quite right yet. The release date moves, and then moves again.

This is not laziness. It's usually the opposite. Developers in this loop are often working hard, making real progress, and genuinely improving the game. The problem is that they are optimizing for the wrong thing. They are practicing the skill of building, not the skill of finishing.

Building and finishing are not the same thing. They require different instincts, different habits, and a different relationship with the work itself. And for indie developers working alone or in small teams, the gap between those two skills is often what determines whether a game ever releases.

---

## Why Finishing Feels Unnatural

When you are actively building a game, there is always something to do. Something to fix. Something to add. Something to improve. That forward momentum is one of the great pleasures of development. The game is becoming something. Every week it is a little better than it was before.

Finishing interrupts that momentum. It requires you to stop adding and start subtracting. Features that seemed important have to be cut. Systems that could be better have to be declared good enough. The satisfying feeling of making progress gets replaced by the uncomfortable feeling of drawing a line.

The trap is that cutting and stopping feel like failures of ambition. They feel like settling. A developer who truly cared about the game would add that extra mechanic, right? Would polish that one rough section, wouldn't they?

That instinct is understandable but wrong. Shipping is not settling. It is a different kind of work, one that requires the same discipline and care as building — just pointed in a different direction.

---

## The "One More Thing" Loop

Most unfinished games didn't fail because the developer ran out of ideas. They failed because the developer couldn't stop having them.

This loop tends to look the same in every project. The game is roughly complete. It plays well. The core experience is there. But there are three things that feel missing. So those three things get added. During that process, two more gaps become obvious. Those get added too. By the time those are done, the original three features have introduced inconsistencies that need addressing. And so it continues.

None of these additions are bad ideas in isolation. The problem is that the loop never closes. The game never reaches a state where nothing feels missing, because the act of adding things creates new gaps. A game that is 90% done can stay at 90% done indefinitely.

The only way out of the loop is to recognize it for what it is and make a deliberate decision to exit. That decision isn't made by the game. It has to be made by the developer.

---

## What "Ready to Ship" Actually Looks Like

Here is something worth admitting: no game is ever truly finished. There will always be something that could be better. A released game is not a completed game. It is a game that crossed a threshold the developer defined and held to.

The question is never "is this game perfect?" It is always "is this game worth someone else's time?"

Those are very different questions, and the second one is much more answerable. Worth someone's time doesn't mean flawless. It means the experience holds together. The core loop works. The rough parts don't break the experience. Someone who downloads this game will find something real on the other side of it.

A useful practice is to separate two different lists: a list of things the game needs before it ships, and a list of things the game would benefit from eventually. The first list has to be finite and defensible. If every idea ends up on the first list, it's not really a needs list — it's a wishlist with extra steps.

Maintaining that distinction under pressure is harder than it sounds. When a feature feels important, it's easy to convince yourself it belongs on the first list. Developing the judgment to push it to the second list — without feeling like you're betraying the project — is what shipping as a skill actually looks like.

---

## Shipping Teaches You Things Building Doesn't

There is information you can only get by releasing.

You learn which parts of the game players notice and which parts they ignore. You learn what your actual audience is, which is often not the audience you imagined. You learn what kind of feedback is useful and what kind isn't. You learn how the game reads to someone encountering it for the first time, without all the context you've accumulated over months of development.

None of that information is available during development. No amount of internal playtesting or imagining what players will think is a substitute for seeing what players actually do.

Developers who ship regularly build up a body of that knowledge. Each release teaches them something the next project benefits from. Developers who don't ship — who keep refining the same project indefinitely — are optimizing against an imaginary standard instead of a real one.

---

## What This Means for Project Echo

Project Echo is in a phase of development where the tension between building and finishing is becoming real. The core mechanic — switching between Past and Present to solve puzzles — is working. The puzzle logic holds up. There are levels. There is a playable game.

There are also features I haven't built yet. Puzzles I want to add. Visual polish that isn't done. Transitions that could feel smoother. That list is not going to get shorter on its own.

What I'm working on now is building the two lists I described earlier. The first contains what the game genuinely needs before it's ready for anyone else to experience. The second contains everything I'd like to do eventually, which is longer and will stay longer. Keeping those lists separate — and being honest about which list something belongs on — is one of the most important things I can do for the project right now.

The game that ships is more valuable than the game that never does, however good the unreleased version might eventually have been.

---

## Final Thought

Building a game and finishing a game are different disciplines, and indie developers rarely practice the second one enough before needing it.

**The most important release isn't a perfect game — it's the one that actually gets out the door.**
